## Original RED-stage proposed implementation (historical)

1. Migrate exact source definitions and a Catalog-owned reconciler. New records and missing links are inserted; existing records receive only the source-authorized corrections above. Do not seed supplier prices from Web reference-cost documents.
2. Register an awaited startup service in actual Program. Reconciliation defaults off and requires explicit owner-controlled enablement. Enabled startup becomes ready only after successful reconciliation/cache handling. No unconditional seeding, HasData, startup DDL/migration, public mutation route or dormant-helper-only completion claim.
3. Proposed transaction policy: one Material-owner PostgreSQL transaction, acquire consistently ordered write-exclusive locks on the six touched tables before reading, then reconcile/save/commit. A 60-second lock wait bound is proposed from the source contract, subject to root review and disposable concurrency/timeout tests. Source SQL Server sp_getapplock must not be transplanted. Lock failure/cancellation/ambiguous case-insensitive catalog names must roll back and refuse readiness; no arbitrary duplicate-ID selection or schema uniqueness migration. This policy deliberately coordinates ordinary CRUD writers as well as cooperating startup workers; its operational blocking requires reviewed activation.
4. Strictly invalidate the existing material/group/color/finish cache keys before readiness. Current ICatalogCache.RemoveAsync catches failures, so its best-effort return cannot prove invalidation. Use reviewed strict actual-backend invalidation or a reviewed cache-visibility design, without silently changing general fail-open CRUD policy. Commit-before-invalidation failure must report startup failure; a fresh startup must safely recover idempotently. Multi-instance stale-read/cache races require coordinated activation/drain and remain explicit, not solved by local startup gating.
5. Before any persistent activation: prove real PostgreSQL rerun/concurrent startup, exact IDs/links, intermediate-save rollback, timeout/cancellation and startup/readiness/cache failure paths. Coordinate migrated Web material-key/pricing/profile consumers and historical order/quote acceptance. Web fulfillment uses existing printable/colors/surfacefinishes routes and persists numeric MaterialId/ColorId/SurfaceFinishId. No DTO/route/schema change is proposed.
